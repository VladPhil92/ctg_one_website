# Wallet Lifecycle Correlation & Durable Alerts V1

This phase adds operational correlation and durable stuck-state alerts without changing wallet financial authority.

## Privacy boundary

`operational_correlation_id` is an opaque UUID generated by PostgreSQL. It is not a user id, authentication token, idempotency key, transaction reference or settlement authority.

`wallet_chain_operational_alerts_v1` intentionally stores only the intent foreign key, operational correlation UUID, alert kind, lifecycle status, submitted age, confirmation count and alert timestamps/state. It does not store canonical user ids, transaction hashes, wallet addresses, destination addresses, amounts or private-key material.

## Alert lifecycle

The existing reconciliation worker remains the only background observer. When an intent exceeds `WALLET_CHAIN_STUCK_AFTER_SECONDS` it idempotently records one of:

- `submission_stuck`
- `reconciliation_stuck`
- `confirmation_stuck`

Repeated worker passes update the same alert. A terminal `reconciled` or `failed` observation resolves open alerts for that intent. Alert persistence cannot change the chain observation, intent financial fields, COP balance or COP journal.

## Logging

Worker lifecycle logs use `wallet_correlation_id` for cross-run operational correlation. Do not add user ids, transaction hashes, wallet/destination addresses or amounts to these log events.

## Rollout

Deploy migration 0090 before relying on durable alerts. Keep `WALLET_CRYPTO_SEND_EXECUTION_MODE=disabled` during rollout. This phase does not enable a canary artifact or real Polygon broadcast.
